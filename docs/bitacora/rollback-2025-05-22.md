# Rollback / Decisiones — 2025-05-22

Registro de decisiones técnicas tomadas durante el bulk de tareas 8-22.

---

## 3D Location — Modelo homogéneo vs Layer-cake

**Decisión:** Usar modelo de velocidad **homogéneo** (Vp, Vs constantes) en vez de layer-cake.

**Justificación:**
- Velocidad de implementación: layer-cake requiere integrar 1/V(z) por capa, mayor complejidad
- Error aceptable: para clínico/monitoreo, ±5 km de profundidad es suficiente
- Datos disponibles: sin well-log o tomografía local, no hay información para calibrar capas

**Trade-off:**
- No modela interfases de velocidad reales (importante para corteza superior)
- En eventos someros (< 5 km) el error puede ser mayor

**Alternativa futura:** Agregar `VelocityLayer` dataclass y `locate_event_layer_cake()` cuando se tenga información de stacking velocity.

## 3D Location — Station.z = 0 por defecto

**Decisión:** `Station.z`默认值 = 0 (estaciones superficiales), se permite z ≠ 0 para boreholes.

**Justificación:**
- Todas las estaciones del proyecto son de superficie (sin boreholes instrumentados)
- Los datos de elevación de ObsPy (`stats.elevation`) no se usaban anteriormente
- Para MVP se mantiene simple

**A futuro:** Leer `stats.elevation` de ObsPy traces y usarlo para Stations reales.

## Ollama — Fallback a cloud en mismo proceso

**Decisión:** No implementar switching dinámico Ollama→OpenRouter a nivel de modelo.

**Justificación:**
- `dynamic_config.py` solo soporta un modelo global por configuración
- El overhead de mantener dos configs dinámicas complica el flujo
- La UI ya tiene selector de modelo manual — el usuario puede elegir

**A futuro:** Crear `create_task_aware_agents_config()` que mapeé cada tarea a un modelo diferente cuando se tenga demanda real.

## Docker — Multi-stage builder vs single stage

**Decisión:** Multi-stage con builder + runtime, todos los apt-build-packages en el stage builder.

**Justificación:**
- Imagen runtime: ~800 MB vs ~2 GB single-stage
- Build tools (gfortran, OpenBLAS dev) no necesarios en producción
- Los runtime libs (libopenblas0, liblapack3) son compartida-objects suficientes

**Trade-off:**
- Build más lento la primera vez (dos pip install)
- Mejor cache con `COPY requirements.txt` antes de `RUN pip install`

## Logging — pythonjsonlogger como dependencia opcional

**Decisión:** `pythonjsonlogger` es **opcional**: si no está instalado, se cae a formato texto.

**Justificación:**
- No todas las instalaciones de producción van a necesitar logging JSON
- Si `pip install -r requirements/base.txt` incluye `pythonjsonlogger`, se activa
- El fallback texto evita que el servicio no arranque si falta el paquete

---

## PyInstaller spec — Sin console para app, con console para CLI

**Decisión:** Dos executables: `SeismoAnalyzerPro` (sin console, GUI Streamlit) y `seismo_cli` (console, batch).

**Justificación:**
- Streamlit app es navegador-base, no necesita terminal
- La CLI (`src/cli.py`) es útil para batch processing offline
- Separar reduce tamaño y evita popup de cmd.exe en Windows

## requirements.txt — No instalar dev deps en producción

**Decisión:** Mantener `requirements.txt` original (merged) para backward compat, agregar `requirements/base.txt` y `requirements/dev.txt`.

**Justificación:**
- No romper `pip install -r requirements.txt` en entornos existentes
- Productores que hacen `docker build` usan solo `base.txt`
- Desarrollo usa `dev.txt`

## scripts/load_demo.sh — Copia archivos en vez de symlink

**Decisión:** El demo copia datos de `data/AC-1-SUR/` a `data/demo/` en vez de usar symlinks.

**Justificación:**
- Los datos reales en `data/` pueden ser grandes ( GBs)
- El demo puede funcionar sin datos reales usando la estructura ya existente
- Si no hay datos en `data/`, el script falla de forma clara con instrucciones

---

## API location endpoint — Coordenadas sintéticas si no hay lat/lon

**Decisión:** Si la traza no tiene lat/lon en metadata, usar disposición circular sintética de estaciones (radio=10 km).

**Justificación:**
- El servidor location actual (`server.py:961`) creaba todas las estaciones con x=y=0.0
- Esto hacía la localización trivial e inútil
- La disposición circular es el fallback estándar en geofísica cuando no se conocen coordenadas

**Limitación:** La localización absoluta en coordenadas geográficas requiere que las trazas tengan lat/lon en su metadata ObsPy.

## test_three_d_location.py — Usar `station` como objeto Station en PSObservation

**Cambio de API:** `PSObservation.station` ahora es un objeto `Station` (no string).

**Impacto:**
- Todos los callers que usan `o.station` como string requieren update
- `locate_event_1d` internally crea `Station(code=s, x=v["x"], y=v["y"])` en server.py

**Razón:** Permite acceso a `station.x/y/z` directamente en `_dist_3d()`, sin lookup adicional.
